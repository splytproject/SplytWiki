> **In plain terms:** Bitcoin addresses end in a short checksum that catches typing mistakes. The checksum used for early SegWit addresses had a blind spot. BIP-350 swaps in a corrected checksum, called bech32m, for Taproot and later address types.

**BIP-350** defines **bech32m**, a variant of the bech32 address encoding. It changes the rules for native [Segregated Witness](../Segregated_Witness/) addresses of witness version 1 and above.[^bip350] Version 0 addresses keep the original bech32 format from [BIP-173](../BIP_index/#bip-173).[^bip350] The first output type to use bech32m is [Taproot](../Taproot/), defined in [BIP-341](../BIP_index/#bip-341).[^bip341]

## What problem it solves

### The bech32 insertion flaw

Bech32, specified in BIP-173, encodes SegWit outputs as text such as `bc1q…`. Its last six characters are a checksum designed to catch typing errors.[^bip173]

BIP-350 describes a weakness found later. When a bech32 string ends in `p`, inserting or deleting any number of `q` characters just before that `p` leaves the checksum valid.[^bip350] A mistyped address could therefore pass validation.

### Why version 0 was safe but later versions were not

Version 0 witness programs must be exactly 20 or 32 bytes, under [BIP-141](../BIP_index/#bip-141). A wallet rejects a version 0 address of any other length.[^bip350] That length check catches the extra or missing characters.

Later witness versions may use any program length from 2 to 40 bytes. For them, the length check gives no protection, so the checksum must work on its own.[^bip350]

### Checksum quality

BIP-350 measures error detection against a 30-bit hash-based checksum. Such a checksum misses any given error pattern with probability 2⁻³⁰.[^bip350]

Bech32 always detects up to four substituted characters. However, the `q`-insertion case gives one simple error pattern a miss probability of 2⁻¹⁰.[^bip350] Bech32m aims to keep the substitution guarantee while making other common errors no worse than a hash-based checksum.[^bip350]

## How it works

### The one-constant change

Bech32 and bech32m share the same alphabet, generator polynomial and human-readable parts (HRPs), such as `bc` for mainnet. The only difference is the constant XORed into the checksum at the end:[^bip350]

| Encoding | Final constant |
|---|---|
| Bech32 (BIP-173) | `1` |
| Bech32m (BIP-350) | `0x2bc830a3` |

The checksum is computed with the BCH-code function `polymod` over the expanded HRP and the data. A string is valid bech32m when:[^bip350]

    polymod( hrp_expand(hrp) || data ) == 0x2bc830a3

A string cannot be valid under both encodings at once.[^bip350]

### Which addresses use which encoding

BIP-350 sets a rule based on witness version:[^bip350]

| Witness version | Encoding | Mainnet example prefix |
|---|---|---|
| 0 (P2WPKH, P2WSH) | Bech32 | `bc1q` |
| 1 to 16 | Bech32m | `bc1p` for version 1 |

A decoder must check that the encoding matches the version. A version 0 address with a bech32m checksum is invalid. So is a version 1 or higher address with a bech32 checksum.[^bip350]

### Decoding rules

BIP-350's reference decoder rejects an address if any of these hold:[^bip350]

- The HRP does not match the expected network.
- The witness program is shorter than 2 or longer than 40 bytes.
- The witness version is above 16.
- A version 0 program is not 20 or 32 bytes.
- The checksum encoding does not match the witness version.

### How the constant was chosen

The authors restricted the redesign to changing the final constant, which keeps implementations simple.[^bip350] They began with every 30-bit constant other than `1`: 2³⁰ − 1 candidates. Exhaustive analysis of error patterns then filtered them. After the second filter, 12,054 candidates remained, and after the third, 79. A final tiebreaker selected `0x2bc830a3`.[^bip350]

## Status and deployment

As of October 2026, BIP-350's header status is **Deployed**.[^bip350] Under [BIP-3](../BIP_index/#bip-3), Deployed means a settled proposal with evidence of active use.[^bip3]

| Software | Support | Source |
|---|---|---|
| Bitcoin Core 0.21.1 (May 2021) | RPCs require and output bech32m for version 1+ addresses (PR #20861) | Release notes[^core-0211] |
| Bitcoin Core 22.0 | Wallet can generate bech32m addresses (`OutputType::BECH32M`, PR #22154) | Release notes[^core-22] |
| Bitcoin Core 23.0 | GUI address-type dropdown includes bech32m; `validateaddress` reports `error_locations` | Release notes[^core-23] |

| rust-bech32 | Implements bech32 and bech32m | Project README[^rust-bech32] |

Bitcoin Optech tracked wider wallet support during 2021, including Electrum 4.1.0 and Sparrow 1.4.3.[^optech-bech32]

## Criticism and alternatives

**Deliberate loss of forward compatibility.** BIP-173 had asked wallets to accept any future witness version. BIP-350 breaks that: older software cannot pay bech32m addresses.[^bip350] The authors call this intentional. They argue that a clean break also protects old software from the mutation flaw.[^bip350]

**Wallets had to upgrade.** Every wallet or service paying Taproot addresses needed new code. Version 0 addresses needed no change.[^optech-bech32]

**Alternative: keep bech32 for some lengths.** A design that kept bech32 for certain future addresses was considered on the bitcoin-dev mailing list in November 2019.[^ml-2019] It was discarded in December 2020.[^ml-2020-12]

**Little was lost, the authors argued.** Testing by Taproot proponents found that hardly any wallets could send to higher witness versions anyway.[^ml-2020-11] Those tests also found software that would have burned funds when paying version 1 addresses. Under bech32m, such software rejects the address instead.[^bip350]

## Developer notes

### Reference implementations

- Reference encoders and decoders in Python, C, C++ and JavaScript are in the [sipa/bech32](https://github.com/sipa/bech32) repository, under `ref/`.[^bip350]
- An error-locating JavaScript decoder is under `ecc/javascript` in the same repository.[^bip350]
- In Bitcoin Core, `src/bech32.h` defines `Encoding::BECH32M` and the `LocateErrors` function.[^core-bech32]

### Relevant RPCs (Bitcoin Core)

- `getnewaddress "" bech32m` returns a Taproot address from a descriptor wallet (22.0 and later).[^core-22]
- `validateaddress <address>` decodes bech32 and bech32m addresses. It returns `error_locations` for invalid ones (23.0 and later).[^core-23]
- Since 0.21.1, every RPC that accepts addresses requires bech32m for witness version 1 and above.[^core-0211]

**Invalid addresses**

    bc1p0xlxvlhemja6c4dqv22uapctqupfhlxm9h8z3k2e72q4k9hcz7vqh2y7hd   bech32 checksum on a v1 address
    bc1qw508d6qejxtdg4y5r3zarvary0c5xw7kemeawh                       bech32m checksum on a v0 address
    bc1pw5dgrnzv                                                     program length 1 byte

The first valid address encodes the x-coordinate of the secp256k1 generator as a version 1 program. Re-encoding that program with the old bech32 constant produces exactly the first invalid address above. Both results were reproduced for this article with an independent encoder.

### Minimal checksum check

```python
BECH32M_CONST = 0x2bc830a3
GEN = [0x3b6a57b2, 0x26508e6d, 0x1ea119fa, 0x3d4233dd, 0x2a1462b3]

def polymod(values):
    chk = 1
    for v in values:
        top = chk >> 25
        chk = (chk & 0x1ffffff) << 5 ^ v
        for i in range(5):
            chk ^= GEN[i] if (top >> i) & 1 else 0
    return chk

def hrp_expand(hrp):
    return [ord(c) >> 5 for c in hrp] + [0] + [ord(c) & 31 for c in hrp]

# valid bech32m: polymod(hrp_expand(hrp) + data) == BECH32M_CONST
```
